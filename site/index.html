How it works

Seven stations from a report to production

Agents do the judgment work; plain CI and the shipmill CLI do the releasing. The release side works without the agents, so you can start there.

  1. Intake

    agent

    Feature requests and discussions grouped into opportunities you accept or decline

  2. Triage

    agent

    A verdict on every issue (implement, feature, postpone, clarify), with a comment and labels

  3. Fix

    agent

    The issue verified against main, fixed with a regression test, opened as a pull request

  4. Land

    agent

    Each pull request reviewed in its own worktree, small problems fixed, merged only on green CI

  5. Release

    policy

    Cut on its lane when the policy says one is due, CI run on that exact commit, tagged and published

  6. Deploy

    policy

    Health checks, bake time, promotion between environments, rollback that opens an incident

  7. Watch

    agent

    A stalled release, a missing upload, an unannounced fix: reported and finished

You stay in charge

Turn each stage up as you start to trust it

Every stage runs at observe, propose or act. Start with agents that only comment, then let them open pull requests, then let them merge. One file, shipmill.toml, holds the whole policy and goes through review like any other code.

Ask shipmill status what needs you. It answers stuck, waits on you, working or idle, with a link to each item.

One issue stops everything

Open a shipmill-hold issue, from your phone if you must, and no agent or lane moves until you close it.

Release lanes

Most users get releases that real users already ran

Each pull request adds its own CHANGELOG entry, and the entries decide the next version. Installers skip dev and rc unless asked, so someone who needs a fix today pins the pre-release while everyone else waits for a stable one that soaked.
